# 条目评论与事件时间线（P0）

> 状态：**P0 + P1 已实现**（2026-11-14）。P2（跨语言别名、外部补搜）未做。

## 入口

不设固定的"时间线"按钮：每条新闻的 💬 打开评论串，在评论里 `@agent` 触发整理。

```
条目「黄仁勋辞任英伟达 CEO」
  └─ 💬 评论
      └─ @agent 整理一下这件事的时间线
          └─ AI 回复：时间线卡（阶段 / 来源 / 缺口 / 待确认）
```

## 实现

| 层 | 内容 |
|---|---|
| 数据 | schema v8：`chat_threads` 增加 `scope`（brief/item）与 `item_id`；一条新闻一段评论串 |
| 检索 | `app/event-timeline.ts`：从标题/评论抽实体词（剥掉"辞职/卸任/发布"等事件词），用本地 FTS 找相关条目 |
| 合并 | 同 URL 或标题相似度 ≥0.55 的报道合并，保留多来源 |
| 整理 | `main/item-timeline.ts`：一次模型调用，要求只输出 JSON；失败/未配置模型时退回按日期整理的确定性时间线 |
| 校验 | `sourceItemIds` 必须真实存在，非法引用整段丢弃；单来源自动标 `single-source` |
| UI | `TimelineCard`：阶段、状态（已确认/报道/未证实）、来源链接、时间缺口、待确认问题 |

## 提示词约束

- 只允许使用传入素材，禁止补充外部事实
- 每条必须带来源 id；没有引用的阶段被丢弃
- 官方/一手标 `confirmed`，媒体 `reported`，未证实 `rumor`
- 断档写进 `gaps`，未解问题写进 `openQuestions`

## P1：意图与持续跟踪（已实现）

### 意图区分

评论里的 `@agent` 先分意图，再决定要不要落库：

| 说法 | 意图 | 行为 |
|---|---|---|
| `@agent 帮我盯着 / 跟踪 / 关注这件事` | track | 建 story，整理一次时间线，之后持续匹配 |
| `@agent 别再跟踪了 / 取消跟踪` | untrack | 归档 story，停止匹配 |
| `@agent 整理一下时间线 / 梳理来龙去脉` | timeline | 只整理一次，不落库 |
| `@agent 这是真的吗 / 英伟达回应了吗` | ask | 普通问答（剥掉 mention），不建 story |

规则在 `app/agent-intent.ts`：停止 > 跟踪 > 时间线 > 问句；不调模型，省一次往返。

### 跟踪与刷新

- schema v9：`stories` / `story_items`
- 别名只从新闻标题抽实体（评论里的"帮我盯着"不是实体，混进去会误匹配）
- 每次采集结束（`runDaily`）调用 `runStoriesAfterCollect`：
  - 命中新条目 → 写 `story_items`，在发起跟踪的评论串追加「新增 N 条进展」
  - 没命中 → `missCount + 1`
- 评论串里的时间线卡底部显示「跟踪中 / 停止跟踪」

### 连续无进展时主动询问

- 连续 **3 次**采集没有新命中 → 进入待询问
- 应用启动或简报更新时，`TrackingReview` 弹窗：
  > 「事件名」已经连续 3 次采集没有新进展。继续跟踪会保留它，之后有新报道会追加到评论串。
  - **继续跟踪**：清零计数，进入下一个观察周期
  - **放弃跟踪**：归档，不再匹配
- 同一事件两次询问至少间隔 **7 天**，避免天天弹

## 已知限制

- **只覆盖本地已采集的数据**（当前 782 条，从 2026-11-01 起），更早的历史无法回填
- **别名依赖规则**：中文"辞职"和英文"resign"不会自动互搜；同一事件换了说法可能漏
- **别名只来自标题**：事件后续换了说法（"辞职" → "卸任"）可能匹配不到；P2 再做别名扩展
- **匹配按发布时间**：采集时间晚于上次检查、但发布时间更早的旧文不会补进来
- **无进展询问在启动/更新时出现**：应用没开的时候不会推送系统通知
