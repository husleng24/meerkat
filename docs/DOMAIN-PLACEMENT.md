# 领域切换器放在哪：调研与结论

> 状态：调研 + 方案，未实现。2026-11-01。
> 问题：现在「领域」在侧栏最顶部、常驻展开成一个列表。这个位置合适吗？有没有更符合习惯、
> 用起来更方便清晰的位置？

---

## 一、先分清两件事

「领域」是**作用域**（scope）：它改变「今日」「时间线」显示哪一份数据。
它不是一个页面，也不该和「今日 / 搜索 / 时间线 / 源 / 设置」这排**导航**混成同一层。

所以问题不是"把它放在哪一行"，而是：**作用域切换器应该出现在应用界面的哪一层。**

---

## 二、调研

### 2.1 Slack —— 左上角，切换器形态

工作区图标在**左上角**，点开列出所有已登录工作区；`⌘⇧S` 可以把工作区列表常驻在侧栏。

> "Click on your workspace icon in the **top left** to view a list of all the workspaces
> you're signed in to." —— [Switch between workspaces](https://slack.com/intl/en-in/help/articles/1500002200741-Switch-between-workspaces)

### 2.2 Multica —— 左上角，点开切换/创建

侧栏顶部就是工作区名，点开可以切换或新建；下面才是聊天、任务、智能体等导航项。

> "点击侧边栏顶部的工作区名称，选择创建工作区" —— [完整教程](https://multica.ai/docs/zh/tutorial)

### 2.3 Readwise Reader —— 没有作用域，侧栏本身就是视图列表

Home / Library / Feed / Search 固定，其余视图可 pin / 排序 / 管理。

> [Navigation](https://docs.readwise.io/reader/docs/faqs/navigation)

启示：只有当"侧栏 = 视图列表"时，才不需要单独的作用域切换器。我们的侧栏是**导航**，
领域是导航之外的一层，所以必须单独表达。

### 2.4 macOS 的习惯：身份在标题栏，作用域在工具栏

macOS 里"我在看什么"通常写在标题栏（文档名），"在哪一层"可以用工具栏的选择器（如 Xcode 的 scheme）。
但这条对我们**成本太高**：`titleBarStyle: hiddenInset` 只在 macOS 成立，Windows 上要自绘标题栏才
有同样的位置，而这是一个 Windows 优先的应用。

### 2.5 归纳

| 模式 | 谁在用 | 适合 |
|---|---|---|
| 左上角切换器 | Slack / Multica / Notion / Linear | 作用域少而重，切换频率中等 |
| 侧栏常驻分组 | 少数（如 Feedly boards） | 作用域本身就是导航的一部分 |
| 标题栏 | macOS 原生应用 | 单窗口单文档；跨平台成本高 |
| 内容区 tab | 后台类产品 | 同一数据的切片，不改变导航语义 |

**结论：位置放在左上角是对的**（三个协作产品都这么做）。现在的毛病不是位置，而是**形态**——
把"切换器"做成了"常驻列表"：占掉约 150px，并且和导航项长得一样，两层混在一起。

## 三、五个候选位置

![位置对比](assets/domain-placement-mockup.png)

| 方案 | 符合习惯 | 当前作用域可见 | 占用高度 | 扩展性 | 跨平台成本 | 新建入口 |
|---|---|---|---|---|---|---|
| **A 顶部常驻列表（现状）** | ✅ | ✅ | ❌ 约 150px | ⚠️ 多于 6 个要滚动 | 低 | ✅ 就地 |
| **B 顶部单行切换器 + 弹层** | ✅ | ✅ | ✅ 约 34px | ✅ 弹层可滚动 | 低 | ✅ 弹层内 |
| C 窗口标题栏 | ⚠️ macOS 是习惯，Windows 不是 | ✅ | ✅ 0 | ✅ | ❌ 需自绘标题栏 | ⚠️ 弹层 |
| D 内容区标题旁 | ⚠️ 更像"筛选"不是"作用域" | ✅ | ✅ 0 | ✅ | 低 | ❌ 要另找地方 |
| E 侧栏底部 | ❌ 账号切换才放底部 | ⚠️ 要滚到底 | ✅ | ⚠️ | 低 | ❌ |

## 四、推荐：B —— 一行切换器 + 弹层

```
┌──────────────────────┐
│ 领域  AI 综合 ●   ▾  │   ← 34px，当前作用域常驻可见
├──────────────────────┤
│ 今日                 │
│ 搜索                 │
│ 时间线      2026-11-01│
│ 源               15  │
│ 设置                 │
└──────────────────────┘

点开后：
┌──────────────────────┐
│ 切换领域              │
│ ● AI 综合    63   ⌘1 │
│   芯片与算力  68   ⌘2 │
│   具身智能    63   ⌘3 │
│   开发者工具  —    ⌘4 │
│ ──────────────────── │
│ ＋ 新建领域           │
│ 管理领域…             │
└──────────────────────┘
```

理由：

1. **位置符合习惯**：三个参照产品都在左上角表达作用域
2. **作用域始终可见**：不需要展开就知道自己在哪个领域（列表形态折叠后就丢了这条）
3. **只占 34px**：把 150px 还给导航与内容
4. **扩展性**：8 个以上领域时弹层滚动即可，常驻列表会一直占高度
5. **把"切换"和"管理"分开**：弹层里切换，`管理领域…` 跳设置页——和 Readwise 的 Manage views 同一个思路

交互细节：

- 行内显示未读点；不加条数（弹层里再显示，保持标题行短）
- `⌘1–9` 直接切（已有）；弹层里 `↑↓ + Enter`、`Esc` 关闭
- 弹层宽度 206px，与侧栏同宽，从切换器下方展开（不居中、不遮导航）
- 内容区的领域 chip **保留但只作标签**，不再承载点击——避免出现两个切换入口
- 关闭状态不记忆：每次打开先看当前值，弹层本身不需要持久化

---

## 五、为什么不选其他

- **C 标题栏**：macOS 上很自然，但 Windows 需要 `titleBarStyle: hidden` + 自绘最小化/关闭按钮，
  而且拖动区域、红黄绿位置都要自己处理。为一个 34px 的位置付这个成本不值。
- **D 内容区标题旁**：它更像"筛选这一页"，而不是"切换整个作用域"；「时间线」「源」跟着变时会显得突兀。
- **E 侧栏底部**：底部是账号/设置的位置，作用域放那里会让人以为要滚到底才能换。
- **A 常驻列表**：能用，但把两层混在一起，且折叠后又丢了"当前作用域"的信息——这也是这次要改的原因。

## 六、实施拆分（约半天）

1. `Sidebar`：把现在的折叠列表换成单行切换器（`领域  AI 综合 ●  ▾`）
2. 新增 `DomainSwitcher` 弹层组件：列表（名称 + 条数 + ⌘n）、新建、管理入口；点击外部/Esc 关闭
3. 键盘：保留 `⌘1–9`；弹层内 `↑↓/Enter/Esc`
4. 设置页「领域」区块保留（管理入口指向它）
5. 组件测试：弹层开合、键盘选择、当前项勾选、未读点

## 七、验收

- 侧栏高度：领域区域 ≤ 40px（现状约 150px）
- 任何时候都能看到当前领域与未读状态，不需要展开
- 切换步骤：`⌘n` 一步；鼠标两步（打开弹层 + 选择）
- 领域 ≥ 8 个时弹层可滚动，不撑高侧栏
- 弹层打开时点外部 / Esc 关闭，不误触导航
- 内容区 chip 仍是纯标签，不响应点击

## 八、还没定的

- 弹层里要不要放「管理领域…」？我倾向放，和 Readwise 的 Manage views 一致；也可先去设置页。
- 是否保留"展开成列表"作为偏好项？**不建议**：两套形态会让"领域在哪"重新变得不确定。
