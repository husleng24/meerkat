# 反馈与修复流程

## 入口

应用内 **设置 → 反馈**。三步：

1. 选分类（缺陷 / 功能建议 / 信息源问题 / 其他）
2. 写一句话说清发生了什么
3. 点「生成反馈材料」→ 复制 / 保存为文件 / 打开 issue

## 为什么没有「提交」按钮

因为没有服务器。

一个点了没反应、或者事后根本没人看的提交按钮，比没有按钮更糟——它会让反馈
石沉大海，而用户以为自己已经报过了。

所以这里做的是**生成一份可以直接贴出去的材料**：贴到聊天窗口、issue、邮件里都行。

## 材料里有什么

- 你写的描述
- 版本、平台、时间
- 已脱敏的诊断摘要：源健康度、最近一次运行、日志尾部 30 行

## 材料里**不会**有什么

脱敏在 `src/app/diagnostic.ts`，由 19 个测试守着。以下内容一定会被打码：

| 形态 | 结果 |
|---|---|
| `sk-xxxx` | `sk-***REDACTED***` |
| `Authorization: Bearer xxx` | 保留认证类型，凭证打码 |
| `api_key= / token: / secret= / password=` | 值打码 |
| 邮箱 | `***@***` |
| 32 位以上十六进制串 | `***HASH***` |
| 路径里的用户名 | `C:\Users\zhangsan\…` → `~/…` |

其中一条测试是**把整份材料序列化后整体扫一遍**，而不是逐字段检查——
逐字段会漏掉将来新增的字段。

> 如果你还是担心，生成材料后把「附带诊断信息」取消勾选，只发描述。

## 分级与响应时间

这是对自己的承诺，不是对外的 SLA 话术。

| 级别 | 判定 | 首次响应 | 处理 |
|---|---|---|---|
| **S1 阻断** | 应用起不来、数据丢失、密钥泄露 | **24 小时内** | 72 小时内给出修复或可用的绕行方案 |
| **S2 功能错误** | 功能不对但有替代路径（如某个源抓不到、导出失败） | 72 小时内 | 下一个版本内修复 |
| **S3 体验/建议** | 界面、文案、交互不顺 | 记录即可 | 按影响面排期 |

"72 小时"指的是**从确认问题到给出修复或绕行方案**，不是发版——
发版还要等打包与分发条件（见 README 的 NSIS 限制）。

## 我需要哪些信息

按信息量排序：

1. **现象**：你点了什么、看到什么、期望什么
2. **是否可复现**：每次都能，还是偶发
3. **诊断摘要**（材料里已带）
4. 截图（只在界面上有异常时有用）

不需要：完整日志、系统信息清单、录屏。

## 已知问题（不用报）

| 现象 | 原因 | 状态 |
|---|---|---|
| 采集显示 34/35 源成功 | `r/MachineLearning` 被 Reddit 限流 | 已知限制，不修 |
| 便携版提示"开机自启不可用" | 便携版每次解压到临时目录，注册表路径会失效 | 设计如此 |
| NSIS 安装包缺失 | 本机无法签名 / 生成卸载器被拦截 | 只发 zip 与便携版 |
| 首次启动没有简报 | 还没采集过 | 点一次「立即采集」 |

## 每次修完要做什么

1. 在 `tests/` 里补一个能复现该问题的测试（**先让它红，再修**）
2. 修完跑 `pnpm test` + `pnpm typecheck`
3. 如果改动触及真机行为（窗口/托盘/通知/打包），在 `docs/VERIFICATION-RESULT.md` 里记一笔
4. 发布后把该问题从"已知问题"里移除或改状态

第 1 条是硬要求。没有测试的修复，下次改动会原样复发——这个项目已经踩过：
定时链路没日志、托盘导出是死按钮，都是"看起来写了但没验证"。
