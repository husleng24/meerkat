# 领域 → 主题 两层模型：评估

> 提案：最上级是「领域」，每个领域下有多个「主题（topic）」；添加源时可以选择领域和主题，
> 也可以就地新建领域和主题。状态：评估完成，**后续方案见 [DOMAIN-ROLLUP.md](DOMAIN-ROLLUP.md)**。

---

## 一、和现在差在哪

```
现在（一层）                     提案（两层）
领域 = topic（同一个东西）        领域
  AI 综合                          ├─ AI
  芯片与算力                       │    ├─ 模型与产品
  具身智能                         │    └─ 芯片与算力
  开发者工具                       └─ 机器人
                                        ├─ 具身智能
                                        └─ 人形机器人

源：全局，按主题多对多勾选         源：全局，添加时选领域 + 主题（可多选）
简报：每个主题一条                 简报：每个主题一条（领域有没有简报未定）
排程：每个主题一套                 排程：每个主题一套（或领域一套，未定）
```

注意一个副作用：现在界面上的「领域」其实是这个提案里的 **topic**。真要分两层，
界面文案要再改一次（现在的领域 → 主题，新增真正的领域），最近几轮的命名工作要回滚一半。

---

## 二、关键问题：领域这一层要"做什么"？

两层值不值得，取决于最上面那层除了"装东西"还承担什么。

| 领域的语义 | 它带来的价值 | 是否值得单独建表 |
|---|---|---|
| **A. 纯分组（文件夹）** | 主题多了以后菜单更好扫 | ❌ 一个标签字段就够 |
| **B. 源池**：源属于领域，主题继承 | 加源只需选一次领域 | ⚠️ 会牺牲"同一源进不同主题"的灵活性 |
| **C. 汇总层**：领域有自己的每日简报/排程 | 早上先看"AI 领域今天有什么"，再下钻 | ✅ 这才是真正的产品价值 |

**如果只是为了"给主题分个组"，A 就够，不需要两层实体。**
真正让两层成立的是 C：领域能出一份跨主题的汇总简报，或者领域级排程。这需要新的
`domains` 表、领域级 brief 生成（把多个主题的条目合并再排序）、领域级排程与状态。

## 三、收益与代价

### 收益

1. **规模**：主题到 10 个以上时，一层列表开始难扫；分组能救
2. **加源有归属**：现在加源不知道进哪个领域，两层后至少能选
3. **C 选项**：领域级汇总简报是现在没有的能力

### 代价（按当前代码量估）

| 项 | 影响 |
|---|---|
| 数据库 | schema v4：新增 `domains` 表；`topics` 加 `domain_id`；迁移旧数据（全部归到一个默认领域） |
| 主进程 | `topics:*` 15 处调用要区分 domain/topic；简报、排程、聊天、采集都要带 domain 上下文 |
| 渲染层 | 侧栏切换器变两层（领域切换 + 主题列表）；设置页要两个管理区；引导页要选领域再选主题 |
| 测试 | 352 个测试里所有构造 topic 的地方要补 domain；新增迁移测试 |
| 文案 | 现在的「领域」要改回「主题」，再引入新的「领域」——最近几轮白改 |
| 工期 | 约 **2–3 天**（不含领域汇总简报；含的话再加 1–2 天） |

### 使用成本

- 每天打开应用的第一件事是读简报。现在：**1 次点击**切主题；两层后：**2 次**（领域 → 主题），
  或者侧栏同时展示两层（更挤）。
- 主题只有 3–4 个时，两层带来的额外导航成本大于收益。

---

## 四、建议：分三步，先解决真问题

用户现在真正的痛点是上一轮暴露的：**加完源没有归属**。两层模型能顺带解决它，但成本不成比例。

### 第 1 步（0.5 天，立刻做）

- 新增源表单加「加入主题」多选（默认当前主题），保存时写 `topic_sources`
- 源列表每行显示所属主题；一个都没有的标红「未加入任何主题」
- 这样"加源 → 参与采集"闭环，不引入新概念

### 第 2 步（0.5 天，等主题变多再做）

- 给 `topics` 加一个**可选的 `domain` 文本字段**（不是新表）
- 侧栏切换器按 domain 分组显示；领域名可以留空（不填就是一组"未分组"）
- 这就是 A 选项：80% 的分组收益，10% 的成本，而且随时能升级成真表

### 第 3 步（2–3 天，只有想要领域级简报时才做）

- 建 `domains` 表、领域级汇总简报与排程
- 这一层才真正"多出一层产品能力"，而不只是多一层菜单

---

## 五、需要你定的三件事

1. **你实际会维护多少个主题？**
   - ≤6 个：两层不值得，第 1 步 + 第 2 步足够
   - ≥10 个：第 2 步的分组会明显有用，可以提前做
2. **领域需不需要自己的每日简报**（"今天 AI 领域发生了什么"，跨主题汇总）？
   - 需要：这是 C，值得建 `domains`
   - 不需要：领域只是文件夹，别为它建表
3. **同一个源要不要同时进多个主题？**
   - 要：保持现在"源 → 多个主题"的多对多
   - 不要：可以简化成源只属于一个主题，加源表单也更简单

---

## 六、如果决定做两层，迁移清单

1. `domains(id, name, hour, minute, enabled, created_at)`
2. `topics.domain_id`（迁移时全部指向默认领域"AI"）
3. 简报：仍按 topic 存；C 方案另建 `domain_briefs` 或按需实时聚合
4. 排程：先保持按 topic；领域级排程在 C 阶段再加
5. IPC：`domains:list/create/rename/remove`；`topics:list` 支持按 domain 过滤
6. UI：侧栏 = 领域切换器 + 主题列表；设置页 = 领域管理 + 主题管理（两级树）
7. 加源表单：领域（决定主题候选）+ 主题多选 + 就地新建
8. 测试：迁移（旧库升级后主题不丢、源归属不丢）+ 加源归属 + 两级切换

---

## 七、结论

**方向合理，但现在做偏早。** 两层模型的价值来自"领域级汇总/排程"，
而不是"把 4 个主题装进 2 个文件夹"。先用 0.5 天把加源的归属闭环修掉；
主题确实变多以后，用 `domain` 文本字段分组（0.5 天）就能拿到大部分收益；
等你真的想要"早上先看领域汇总"，再建 `domains` 表——那时两层才名副其实。
